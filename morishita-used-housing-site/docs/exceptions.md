## 2026-08-19 O-04（デプロイはAIが実行しない）の適用除外について

### 経緯

大野の指示により恒久的に変更した。判断の材料として提示した選択肢と、選ばれたもの:

| 論点 | 選ばれた内容 | 選ばれなかった内容 |
|---|---|---|
| 範囲 | デプロイ **＋ DBマイグレーション** | デプロイのみ（マイグレーションは人間） |
| 確認 | **毎回、実行の直前に確認を取る** | 指示されたら確認なしで即実行 |
| 期間 | **恒久的** | 検証段階のみ（期限つき） |

### 残した歯止め

O-04 を外しても、次の4つはAIが実行しない。理由はそれぞれ別にある。

1. **秘密情報の設定**（Vercelの環境変数・APIキー・`NEXTAUTH_SECRET`）
   — S-01。AIに値を渡さない構えを崩さないため。8/18にDBパスワードがチャットへ流出した経緯がある（docs/incidents.md）
2. **リポジトリの可視性変更** — 一度 public にすると取り消せない
3. **破壊的なDB操作**（`migrate reset` / テーブル削除 / WHERE句なしの更新） — D-15 のまま
4. **戻せないマイグレーション**（カラム削除・型変更など） — 個別に承認を得る

### 前提となる環境

この変更を実際に機能させるには、作業マシンに次の2つが要る。2026-08-19 時点でどちらも未整備。

- Vercel CLI（`npm i -g vercel` → `vercel login`。ブラウザ認証のため人間の操作が必要）
- GitHub CLI の認証（`gh auth login`）または push できる資格情報

### 元に戻す場合

CLAUDE.md の D-14 と固有欄の「デプロイ」行を、`OPS_RULES.md O-04 に従う` へ戻す。

## 2026-08-25：本番Supabaseのリージョンを ap-south-1（ムンバイ）のまま運用する

### 経緯

モリシタハウス用の Supabase 新規プロジェクトが **South Asia (Mumbai) / ap-south-1** で
作成された。手順書（docs/本番環境の作り方.md）の推奨は
**Northeast Asia (Tokyo) / ap-northeast-1** で、RENOEL 版もそちらを使っている。

AIから次を提示したうえで、大野が「Bで進める」と判断した。

- 日本の来訪者からの往復が 日本↔ムンバイ になり、片道で概ね150〜200msの遅延が乗る
- 1画面で複数回クエリを投げるページ（物件一覧・管理画面）ほど体感に出る
- **Supabase はプロジェクトのリージョンを後から変更できない**
- 指摘時点ではテーブル0件・データ0件で、作り直しコストは実質ゼロだった

### 期限・見直しの条件

期限は設けない。次のいずれかが起きたら再検討する。

- 表示速度について実際に苦情や指標の悪化が出たとき
- 掲載物件数が増え、一覧ページのクエリ回数が増えたとき

### 元に戻す場合

東京リージョンで新しい Supabase プロジェクトを作り直し、
`pg_dump` / `pg_restore` でデータを移したうえで、Vercel の環境変数
（DATABASE_URL / DIRECT_URL / SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY）を差し替える。
Storage のファイルは別途コピーが要る。**稼働後は停止時間が発生する。**

### 補足（同時に直したこと）

`DATABASE_URL`（Transaction pooler）に `?pgbouncer=true` が付いていなかったため追記した。
これが無いと Prisma が pooler に対して prepared statement を使おうとし、
本番で断続的にエラーが出る。単純な接続テストでは再現しないため気づきにくい。
